# 完整开发

使用能够安全覆盖变更的最轻档位。

## 1. 选择档位

- **标准：** 边界明确、行为已知且容易回退的功能或重构。
- **重大：** 跨层或结构性工作、公共契约、数据/数据结构/协议变更、大范围迁移或存在实质设计不确定性。
- **关键：** 安全、隐私、授权、破坏性或不可逆数据操作、生产发布或受监管行为。

按最高风险维度判定，不能按修改行数判定。明确超出标准档或判级不清楚时，阅读 [references/impact-and-risk.md](references/impact-and-risk.md)。

## 2. 只加载权威上下文

- 读取 DESIGN 中与行为意图相关的章节。
- 读取 ARCHITECTURE 中与边界和不变量相关的章节。
- 只有安装、运行或用户说明可能变化时才读取 README。
- 按受影响概念搜索 LEARNING 与 trace 文件名，禁止顺序通读历史。
- 扩大搜索前先检查源码入口、所有者、接口、测试和已知依赖方。

## 3. 在新方案前完成有限调研

引入新功能、新方法、新依赖、新协议或项目没有成熟先例的方案时，先阅读 [references/research-guide.md](references/research-guide.md)，再确定实现设计。调研应优先权威来源并在证据足够时停止，不得用无限搜索替代项目判断。完全沿用项目现有模式时可跳过，并说明依据。

## 4. 确认重大边界

标准档应从仓库推断安全细节，只有不同选择会改变用户可见行为或范围时才询问。

重大或关键档实施前，确认以下方面中尚未解决且会产生实质影响的事项：

- 目标行为和验收标准；
- 非目标和兼容性；
- 所有权、接口和数据形态；
- 迁移、发布、回退或恢复；
- 安全、隐私、性能和运行限制。

权威项目资料已经回答的问题不得再次询问。

## 5. 规划可独立验证的增量

- 有利于审查或回退时，将准备性重构与行为变化分开。
- 每个增量保持可构建且行为完整。
- 为每个增量定义所需证据。
- 优先使用项目已有模式和基础设施。
- 避免投机式扩展和无关清理。

## 6. 实现与验证

- 标准档完成简短影响检查后直接实施。
- 重大和关键档按检查点推进，每次跨越边界后重新评估范围。
- 实施期间运行定向检查。
- 完成时运行覆盖全部受影响范围的最小聚合检查。
- 后续成功检查已经覆盖先前检查时，除非相关代码后来发生变化，否则不重复验证。
- 关键档必须保留授权、回退、恢复和未验证风险的证据。

## 7. 核对项目知识

- 对照已确认的设计和架构检查实现。
- 当前项目事实、持久经验或 TRACE 证据变化时调用 `sync-project-knowledge`。
- 不得仅为了记录文件变化而修改概述文档。
- 报告交付行为、受影响范围、验证、文档影响和剩余风险。

## 8. 收敛交付

- 只使用已有实现、差异和验证证据回答最小收尾关卡，不因收尾自动增加命令。
- 标准档发现明确缺口时只补最小操作；重大或关键档读取 [references/delivery-closure.md](references/delivery-closure.md)。
- 明确最终状态，不使用“基本完成”等模糊表述。
- 修改代码、测试、脚本、构建配置、数据结构或协议后，提供基于实际差异的 Commit 文稿，不自动执行 `git commit` 或 `git push`。
