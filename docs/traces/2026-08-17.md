## T-165442 · L4 · 将 TRACE 改为追加式修改跟踪

### 16:54:42 · 开始基线

- 状态：进行中。
- 修改前：TRACE 按主题各建一个文件，主要在任务结束后记录结论，不能看到修改基线、方向变化和最终落点之间的关系。
- 目标：像 worklog 一样按日期聚合，但使用稳定任务编号和检查点跟踪修改演进；worklog 保持执行索引职责。
- 预计范围：根规则、新 TRACE Skill、开发/知识/日志 Skill、文档职责、安装审计、历史 TRACE 迁移、BookReader 接入与版本清单。

### 16:56:00 · 调研与方案

- `最终快照` → `追加式事件`：参考 Event Sourcing 保留表达修改意图的有序事件，并用新事件更正旧结论。
- `无关联的过程段落` → `稳定任务编号 + 检查点`：参考 OpenTelemetry 用同一工作单元关联开始、重要事件、结束和状态。
- `所有变化同等详细` → `只追踪重大决策`：参考 ADR 只保留影响结构、质量属性或难回退选择的上下文、取舍和后果。
- 来源：https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing 、https://opentelemetry.io/docs/concepts/signals/traces/ 、https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record 。

## T-171842 · L4 · 增加按需 Spec 驱动能力

### 17:18:42 · 开始基线

- 状态：进行中。
- 修改前：流程包能按 L0-L5 分配开发、验证、知识和 TRACE 成本，但没有稳定规范 ID、需求到测试/实现/验证的长期追溯能力。
- 目标：从 `demo` 的 SDD 中提炼稳定规范 ID、可执行规格、状态和低成本门禁，并作为 L3-L5 按需能力接入，不能让普通缺陷承担完整 SDD。
- 已知边界：任务 TRACE 继续跟踪修改演进；新的规格追溯必须使用独立名称和文件职责；不得固定通读 LEARNING、历史 TRACE 或全部 Spec。
- 预计范围：新增 Spec Skill 与模板，更新根路由、完整开发、精准修复、项目初始化、知识同步、安装审计、版本和概述文档，并升级 BookReader 首个接入项目。

### 17:26:29 · 调研与方案确定

- `demo` 的全任务完整 SDD → 按风险启用轻量/完整 Spec；原因是保留稳定契约能力，同时避免普通缺陷固定读取大型 LEARNINGS、集中 TRACE 和全部 Spec。
- `单一 spec/TRACE.md` → 每份功能 Spec 就近维护追溯表；原因是减少无关上下文、路径陈旧和并发编辑冲突。
- `所有任务强制红灯` → 新行为优先红灯，缺陷、行为不变重构和无法自动化场景分别使用回归测试、基线对比或人工验收；原因是证据必须服务于风险而不是仪式。
- `单一规格强度` → `spec-driven-change` 提供轻量与完整两档，并只检查显式传入的 Spec 文件。
- 外部依据：GitHub Spec Kit 支持可定制的 Spec→Plan→Tasks→Implement；Kiro 区分 Feature、Bug 与 Quick Spec；Agile Alliance ATDD 强调验收测试服务于需求沟通并警告工具反客为主。
- 来源：https://github.com/github/spec-kit/blob/main/docs/index.md 、https://kiro.dev/docs/web/specs/ 、https://agilealliance.org/glossary/atdd/ 。

### 17:32:00 · 最终映射

- 状态：完整完成。
- `无功能级稳定行为契约能力` → 新增 `spec-driven-change`，提供轻量/完整两档和 `SPEC.template.md`；原因是让高影响变更可以跨会话保持验收意图。
- `普通缺陷可能被完整 SDD 放大` → L2 默认跳过，只有缺失/冲突契约或反复回归才启用；L3 按用户可见行为启用轻量档，相关 L4/L5 使用完整档。
- `集中追溯矩阵会持续膨胀` → 每份功能 Spec 就近维护规范 ID、验收、测试或人工入口、实现符号、验证和状态；禁止默认通读全部 Spec。
- `所有任务强制红灯` → 新行为优先实现前失败证据，缺陷、行为不变重构和无法自动化场景使用与风险相称的证据。
- `无低成本规格门禁` → 新增 `check_spec.py`，只检查显式传入文件的必要章节、稳定 ID、追溯映射和模板占位符；它不声明语义正确。
- 路由与知识：AGENTS、完整开发、精准修复、初始化、知识同步、TRACE、worklog、README、DESIGN、ARCHITECTURE、LEARNING 已同步职责。
- 安装/审计：必需 Skill 从六个增加为七个；版本 0.4.0 → 0.5.0；清单增加 `specDirectory`，但安装器不预建空 `spec/`。
- 验证：14 份流程包/BookReader Skill 校验通过；脚本编译、Spec 正例、模板占位反例、缺失映射反例、全新安装、审计正反例、项目专属区保留和差异检查通过；独立前向测试正确区分跳过/轻量/完整三种场景。
- 兼容与风险：新 Skill 保持标准 `SKILL.md` 结构且无厂商专属元数据；已有项目可沿用自己的 Spec 目录。静态门禁只验证结构，语义仍由测试、人工验收和工程审查负责。
